# How docs content is created and generated

Companion to the [style guide](./STYLE_GUIDE.md), which covers *how to write*. This
page covers *where content comes from*: which files are hand-authored, which are
generated, what regenerates them, and which frontmatter fields drive theme features.

## Two kinds of content

| | Hand-authored | Generated |
| --- | --- | --- |
| Where | `content/en/latest/**` (except `api-reference/`) | `content/en/latest/api-reference/**`, `data/api_refs.json`, `data/api_props.json` (the guides' `{{% props %}}` tables) |
| Source of truth | the Markdown file itself | the SDK's own `api-extractor` output (`libs/*/temp/*.api.json`) |
| Edit directly? | yes | **no — wiped and rewritten on every regen** |
| Review | normal docs review | review the generator change, not the output |

Generated pages carry `source: api-documenter` in frontmatter and start with
`<!-- Do not edit this file. It is automatically generated by API Documenter. -->`.

## Regenerating the API reference

The generator lives in this repo, at **`sdk/docs/scripts/generate-reference.ts`**
(run as `OUT_DIR=<dir> npm run api-reference:generate` from `sdk/docs`). It reuses
the SDK's existing pipeline and only adds a Hugo adapter:

```
api-extractor (per lib, run by the SDK build)  ->  libs/*/temp/*.api.json
api-documenter markdown                        ->  one Markdown file per symbol
generate-reference.ts                          ->  Hugo pages + data/api_refs.json + data/api_props.json
```

```bash
# 1. produce fresh api.json (in this repo)
cd sdk && rush install && rush build

# 2. generate the reference output (from sdk/docs)
cd ../docs
OUT_DIR=/tmp/api-ref npm run api-reference:generate
```

What it does:

- publishes one page per `@public`, `@beta` and `@alpha` declaration; `@internal`
  never reaches the model (api-extractor leaves it out). Packages with no `@public` or
  `@beta` declaration (internal-only or all-alpha) are skipped entirely (today: `util`, `sdk-e2e-utils`,
  `sdk-ui-pluggable-application`, `sdk-pluggable-application-model`,
  `sdk-ui-pluggable-host`, `sdk-ui-application-header`).
- `@beta` pages get a **Beta** badge next to the kind (`stability: beta` in
  frontmatter, set from api-documenter's beta notice), `@alpha` pages an **Alpha**
  badge and an "Alpha API" notice (`stability: alpha`, set from the declaration's
  `releaseTag`: api-documenter writes no alpha notice). `api_refs.json` carries
  `stability` so a guide's symbol chips show it too. The line is drawn in
  `PUBLISHED_RELEASE_TAGS` in the generator. Alpha was left out from 2026-09-30 and is
  published since 2026-10-19: public and beta signatures use alpha types and guides use
  alpha APIs, so leaving it out only turned ~250 type names into dead text. `LIBS_TO_SKIP` in the generator mirrors the
  upstream `common/scripts/build-docs.js` blacklist.
- writes `source_path` per symbol by mapping api-extractor's `fileUrlPath`
  (`esm/*.d.ts`) back to `src/*.ts(x)` and checking the file exists.
- writes `usage_pages` per symbol from guide `api_symbols` (see below).
- writes `data/api_refs.json`, the symbol → page lookup the theme uses for
  guide→reference links.
- preserves the site-owned keys on `api-reference/_index.md`
  (`title`, `linkTitle`, `weight`, `legacy_path`, `aliases`) — safe to set them there.

After regenerating: restart `hugo server` (it wedges on 8k-file churn) and delete
stale `public/` directories for pages that no longer exist — this site serves pages
from disk, so a removed page keeps returning 200 until its `public/` output is gone.

## Frontmatter that drives features

Beyond the fields in the [style guide](./STYLE_GUIDE.md#frontmatter):

| Field | Where | Effect |
| --- | --- | --- |
| `api_symbols: ["@gooddata/<pkg>:<Symbol>"]` | hand-authored guides | renders the **API reference** chip panel on the guide, and makes the guide appear as a **Guide:** chip on each symbol's reference page. Also disambiguates auto-linked code spans toward that package. |
| `source_path` | generated | renders the **Source:** chip linking to GitHub. Needs `params.repoURL`; `params.sourceRef` selects the ref (default `master` — pin a `vX.Y.0` tag per release). |
| `usage_pages` | generated | the **Guide:** chips (reverse of `api_symbols`). |
| `kind`, `deprecated`, `package` | generated | kind and Deprecated badges. |
| `nav_leaf: true` | generated package indexes | stops the sidebar from expanding a package's thousands of symbol pages. |
| `diataxis_type: reference` | both | selects the reference layout and skips the section child-card grid. Keyed on this rather than the section name, so the tree can be mounted anywhere. |

If a guide declares a symbol that has no reference page, the generator prints
`WARN: guide api_symbols -> no reference page`. Intentional cases belong in
`scripts/lib/reference-known-misses.json` (typically symbols from excluded packages
such as `sdk-ui-web-components`, or ones that are not public yet). `sdk-ui-ext` (`InsightView`,
`NotificationsPanel`) is generated since 2026-09-30.

## Auto-linked inline code

On guide pages, inline code that names a public SDK symbol is turned into a link to
its reference page automatically (`_partials/guide-body.html`). This covers
incidental mentions in prose; the Props tables carry generated links of their own
(below), which the auto-linker leaves alone. It runs on every hand-authored page,
including component pages typed `diataxis_type: reference`.

Rules worth knowing when authoring:

- a span is linked when it is a type expression: a `` `PascalCase` `` name, an
  array of one (`` `IMeasure[]` ``), or a union (`` `IBucket | undefined` ``). Only the
  PascalCase names inside link, so the span stays one chip and `[]` or
  `undefined` are not clickable. Lowercase members never link.
- lowercase names (`measures`, `onError`) are never linked, since several collide
  with symbol names. Link a function such as `insightTitle(insight)` by hand.
- fenced code blocks are untouched.
- names that don't resolve (React types like `ComponentType`, internal symbols) stay
  plain code — no dead links.
- a name published by two packages is left unlinked unless the page's `api_symbols`
  identify which package it means.
- it degrades to plain code when `data/api_refs.json` is absent, so a checkout
  without a generated reference still builds.

## Props tables

A component guide's `## Props` table is **generated on every build** and never
stored in git. The page holds only the heading and the shortcode:

```markdown
## Props

{{% props %}}
```

`generate-reference.ts` renders the tables from the same pruned model, in the
same run, as the reference pages, and writes them to `data/api_props.json` (one
Markdown table per symbol the guides name). The `props` shortcode prints the
page's table. The table and the reference cannot drift apart, and a new SDK prop
shows up on the next build with nothing to commit.

How a page's table is chosen:

- the page's `api_symbols` are tried in order and the first with a table wins;
  a component (`BarChart`) resolves to its props interface through its first
  typed parameter, an interface is used as is; `props_interfaces` count only when the
  page has no `api_symbols`. A hook whose parameter is an inline object type
  (`useDataExport`) has no props interface, so its page documents the parameters
  by hand;
- own members come first, then inherited ones by walking `extends` across packages;
  own props shadow inherited props of the same name;
- `@public`, `@beta` and `@alpha` members appear (same rule as the reference tree), so
  `@internal` props such as `pushData` are not listed; `@deprecated` props are
  marked `_(Deprecated)_`, `@beta` props `_(Beta)_` and `@alpha` props `_(Alpha)_`
  (only when the prop is less stable than its interface: a beta or alpha interface's
  reference page carries the badge);
- descriptions are the TSDoc summary only, the same cut api-documenter uses in its
  Properties tables; `@remarks` live on the member's reference page;
- every prop name links to its member page, every type token and the "Inherited
  from" interface link to their symbol page. Links are written as
  `apiref:<page path>`; `layouts/_partials/props-markdown.html` turns each into
  the page's permalink, or plain text when the page doesn't exist.

Guards:

- a page with `{{% props %}}` whose symbols have no public props **fails the
  generator** (the table would otherwise vanish);
- a page that still has a hand-written `## Props` table its symbols could now
  generate gets a build warning: replace the table with `{{% props %}}`;
- a page whose symbols aren't published (an `@internal` component) keeps its
  hand-written table. That is the only kind of Props table in git. `@alpha`
  symbols are published, so their pages (`RadarChart`) use `{{% props %}}`.
- the per-page `index.md` renders the page's shortcodes
  (`page-markdown.html`), so `{{% props %}}` becomes its table there too.
- With no `data/api_props.json` (a local build without the SDK api model) the
  shortcode prints a one-line note and the build warns once.

Code: `scripts/lib/api-model.ts` (resolve props from the model),
`scripts/lib/props-table.ts` (render), `scripts/lib/tsdoc.ts` (summaries), tests in
`scripts/tests/`. They were ported from docs-analysis `refresh-props`, which wrote
the tables into the pages and needed a manual `docs:drift` check.

## Agent outputs (llms.txt and Markdown copies)

Following [llmstxt.org](https://llmstxt.org/), the build writes for agents:

- `/llms.txt`: one index, like Anthropic's (`layouts/index.llms.txt`). Every guide page and
  section landing page by section in sidebar order, then the API reference by package (18
  entries) under `## API reference`, and under `## Optional` the full text and the versions
  archive. Each entry links the page's Markdown copy. There is no `llms-api.txt`: a package's
  copy lists its symbols.
- `/llms-full.txt`: every guide page of llms.txt, in the same order, as its Markdown copy, in one
  file (`content/en/llms-full.md`, rendered by `layouts/llms-full.markdown.md` in the MARKDOWN
  format, so shortcodes use the same `.markdown.md` templates). For tools that load a whole
  documentation set at once (Cursor `@Docs`, RAG); Vercel, Supabase, Mantine and Anthropic publish
  one. The API reference is not in it.
- `<page URL>index.md` for **every** page and section: a clean Markdown copy. It is on in
  `config/_default/config.toml` (`[outputs] page` and `section`), so a new page gets one with no
  frontmatter. The theme renders it (`_default/*.markdown.md`, `reference/*.markdown.md`, body in
  `_partials/page-markdown.html`); shortcodes have Markdown versions (`alert.markdown.md`,
  `figure.markdown.md`, `blocks/card.markdown.md`, …; `scripts/tests/llms-exports.test.ts` fails
  on a shortcode the docs use without one). Links point at the linked page's copy, absolute.
- One page per API symbol, in HTML and Markdown: a member (property, method) is a section of its
  parent symbol's page. The generator marks it `folded` (`build.render: link`, `outputs: [html]`,
  left out of the sitemap), so it has no page of its own, and every link to it points at the
  section (`parent/#member`).
- Every HTML page links `rel="describedby"` to llms.txt and `rel="alternate"
  type="text/markdown"` to its copy.

On an API page the article is under 10% of the HTML text (the rest is navigation), so the copy
saves an agent most of the tokens. All copies together are ~11 MB; build time is unchanged.
Folding the members cut the build from ~975 MB to ~347 MB (8.4k member pages were ~78 KB of
site chrome each).

## Search

Portal AddSearch, in every environment, with the key and Kapa "Ask AI" widget id
the live docs use (`config/_default/params.toml`). Its crawl scope must include
the reference subtree, and the extra ~8k pages count against the index quota.

Because the index is hosted and crawled from production, a dev server or PR
preview searches the live site: hits open the production page, not the copy you
are looking at. That is the accepted trade-off. The alternative was a build-time
index (pagefind), which needed a post-build step no pipeline ever ran, so every
preview shipped with no search box at all.

## Current state and open work

### Where the generated reference comes from

The reference is generated inside every docs build. Nothing is committed and
nothing is stored between builds.

- The Hugo build action (`.github/actions/hugo/build-action`) sets up rush, runs
  `rush build --to subspace:sdk` and `rush api-extractor --to subspace:sdk`
  (about a minute with the build cache), then `sdk/scripts/build-api-reference.sh`.
  That script runs `npm run api-reference:generate` in `sdk/docs` into a temp
  `OUT_DIR` and hands it to `sdk/scripts/place-api-reference.sh`.
- `place-api-reference.sh <artifact-dir> <content-dir>` finds each committed
  `api-reference/_index.md` marker, rewrites the URL placeholders
  `__API_REF_BASE__` and `__DOCS_BASE__` to that folder, keeps the marker's
  frontmatter, takes the generated body, and places the tree. `data/api_refs.json`
  comes from the same output. Missing content dir, malformed output, or zero
  markers under `content/en` fail the build.
- Locally, with a reference: `make api-reference`, then `hugo server`. It needs an
  api model — either a built SDK (`sdk/libs/*/temp/*.api.json`) or `SDK_LIBS_DIR`
  pointing at a snapshot laid out as `<pkg>/temp/<pkg>.api.json`. docs-analysis
  keeps such a snapshot under `.reference-tmp/input`; stage it with one `for` loop
  and pass the staged dir as `SDK_LIBS_DIR`.
- Locally, without one: `make web-serve` (or `npm start`). Both pass
  `API_REFERENCE_OPTIONAL=1`, so a missing api model prints the recipe above and
  carries on, and both serve the `local` environment (`config/local/`), where
  `refLinksErrorLevel = "warning"` turns the unresolved reference links in
  guide prose into warnings, and each `{{% props %}}` prints a note instead of
  its table. `/api-reference/` is then empty and its links
  go nowhere; everything else renders. A plain `hugo server` with no `-e local`
  still fails on the first missing link — that is deliberate, so CI, previews and
  production keep treating a broken reference link as an error.
- After a local run, `git status` shows `api-reference/_index.md` modified: the
  body is replaced with the generated package list. Do not commit that change;
  the committed file is only the marker.
- A guide that links a symbol not yet public fails the build with
  Hugo's `REF_NOT_FOUND`; add intentional misses to
  `scripts/lib/reference-known-misses.json`.

### Versioned (production) build: the newest 6 versions

The public build (`HUGO_ENV=public`, `versioned_docs/`) runs
`sdk/scripts/build-api-reference-versions.sh` instead of `build-api-reference.sh`:

- In a preview build (`generate.sh ... keep_master`, e.g. `make web-versions`) `latest/` is
  `master`'s own tree, and `generate.sh` leaves a `.keep_master` marker in `versioned_docs/`.
  `latest/` then gets this checkout's model, and the newest release, which the release bot
  maps to `dirpath = "latest"`, stays in its own `<version>/` folder and gets its reference
  there. In production (no `keep_master`) `latest/` is the newest release, filled below.
  Guide fixes made after a release belong to the latest version's branch, so they reach its
  folder on the next deploy.
- The first `API_REFERENCE_VERSIONS` (default 6) numbered entries of
  `config/public/params.toml` (newest first, kept by the release bot) each get their
  **own** reference: a git worktree of `origin/rel/<version>`, `rush install`, `build`
  and `api-extractor` there, then the generator with that model and that version's
  guides (`GUIDE_CONTENT_DIR`), placed into that version's folder only
  (`PLACE_ONLY=<dirpath>`). A release branch from before the in-site reference has
  no marker; the script copies this checkout's `content/en/latest/api-reference/_index.md`.
- Every other version folder loses its `api-reference/`, so no stale copy is published.
  Its guides' links into it (`relref "/<dirpath>/api-reference/..."`) are rewritten to the
  newest numbered version's reference by `sdk/scripts/relink-api-reference.sh`, so the
  build doesn't fail with `REF_NOT_FOUND`. A symbol the newest version no longer has links
  its package page, or the reference home. The old-version banner
  (`_partials/version-banner.html`) adds "API reference links on this page open the latest
  version (X.Y)" on pages that link the reference or list `api_symbols`.
- The newest version must succeed; an older one that fails is skipped with a warning
  (published without a reference), so an expired build cache never blocks a release deploy.
  Rush's "succeeded with warnings" counts as success.
- Each version's data goes to `data/api_versions/<version, dots as _>/`
  (`api_refs.json`, `api_props.json`, `source.json` with `rel/<version>`). The theme's
  `_partials/api-data.html` picks the page's version, so an 11.58 guide's symbol chips,
  inline links and Props table point at the 11.58 reference, and its Source pills at
  `rel/11.58`. Without its own data a page falls back to the site-wide
  `data/api_refs.json` / `api_props.json`, which are the newest numbered version's
  (a preview build's `latest/` only when no numbered version was built).
- Cost, measured locally for `rel/11.59` without the CI build cache: rush install 2.5 min,
  build 1.7 min, api-extractor 15 s, generator under a minute. In CI the S3 build cache
  and the shared pnpm store (`RUSH_PNPM_STORE_PATH`) make it faster. Output is about
  430 MB per version: ~5.6k HTML pages, plus a Markdown copy of each for the newest
  version only (older versions get none, a `[[cascade]]` in `config/_default/config.toml`).
- More or fewer versions: change `API_REFERENCE_VERSIONS`. Each adds one release-branch
  build to the deploy job, ~5.6k files and ~430 MB to the site. With 6, the deploy is
  ~46k files (estimate; the reference publishes @alpha too since 2026-10-19).
